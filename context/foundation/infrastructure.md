## Recommendation

**Deploy Walkie on Render** (Frankfurt region), using the Rails 8 **Dockerfile path** (not Render's native Ruby runtime — see Getting Started for why), with a paid **Starter** web service ($7/mo) and a **Basic-1GB Postgres** instance with backups ($20/mo). Realistic all-in MVP cost: **~$27/mo**.

Render scored highest on the agent-friendly criteria — GA MCP server (Aug 2025), first-class `llms.txt` / `llms-full.txt` / `.md` URL support, and fully managed Postgres with daily backups co-located in the same region. Heroku is the cheapest viable runner-up at ~$12/mo but carries the Feb-2026 Salesforce "sustaining engineering" signal. Fly.io's Managed Postgres entry pricing (~$38/mo) violates the cost-minimization constraint from the developer interview. The free tier on Render is available but breaks Walkie's "request-to-live in 30 seconds" success criterion (60s cold start) and was rejected explicitly.

### Shortlisted Platforms

#### 1. Render (Recommended)

Wins on the two agent-criteria where the other three lose points: **GA MCP server** (since Aug 2025, hosted at `mcp.render.com/mcp`, narrow mutation surface, Claude Code first-class) and **agent-readable docs** (`llms.txt`, `llms-full.txt`, `.md`-URL trick, `Accept: text/markdown` honored). Managed Postgres with daily backups starts at $7/mo (Basic-256MB) or $20/mo (Basic-1GB). Frankfurt region available. The one Partial — CLI doesn't have a first-class `rollback` command — is mitigated by deploying an earlier commit via `render deploys create` or the dashboard.

#### 2. Heroku (Runner-up)

Cheapest co-located co-located stack (~$12/mo: Basic dyno $7 + Essential-0 Postgres $5). The Heroku Dev Center publishes an explicit **"Getting Started on Rails 8.x"** guide that installs the Solid stack and Thruster correctly — the only platform with documented Rails-8-with-Solid-stack support out of the box. Two Partials: HTML-only docs (no `llms.txt`), MCP server in "early development" (July 2025). The bigger concern is the **Feb 2026 Salesforce announcement** transitioning Heroku to a "sustaining engineering model" with no new Enterprise sales — a real long-term confidence signal, not a blocker for an MVP that will outlive 2026 only if it works.

#### 3. Fly.io

Matches the `tech-stack.md` deployment hint. Has the best Rails-8-aware tooling — `fly launch` runs the `dockerfile-rails` generator and auto-wires Tigris for Active Storage. But **Managed Postgres entry pricing is $38/mo** (Basic plan, 1 GB RAM, shared-2x with HA + backups + pooling), 3–5× more expensive than Render's or Heroku's co-located Postgres. The unmanaged Fly Postgres path is deprecated for new apps. `fly mcp server` is flagged `[experimental]`. No `llms.txt`. The Solid Queue × `auto_stop_machines` foot-gun (jobs queued during machine sleep do not process until an HTTP request restarts the VM) requires explicit `auto_stop_machines = 'off'` config.

## Anti-Bias Cross-Check: Render

### Devil's Advocate — Weaknesses

1. **Render's official Rails 8 guide tells you to scaffold with `--skip-solid`.** The platform's documented path explicitly does not cover Solid Queue / Solid Cache / Solid Cable — the stack Rails 8.1 ships with by default. The moment you keep Solid, you're off the validated path.
2. **Native runtime drops Thruster.** Render's Rails 8 guide uses the native Ruby buildpack; Thruster wraps Puma inside a container. Keeping Thruster forces the Dockerfile path — less-trodden on Render. Dropping Thruster is a deviation from the tech-stack contract.
3. **No Kamal.** Choosing Render means abandoning Rails 8's default deploy tool. The `config/deploy.yml` Kamal config generated by the bootstrapper becomes dead weight, and a future migration to Hetzner / EC2 needs re-engineering.
4. **Solid Queue × Basic-256MB Postgres connection-pool exhaustion.** Each Solid Queue thread holds a Postgres connection. Basic-256MB has a low `max_connections` ceiling — bursty walk-request load can trigger `PG::ConnectionBad` 500s that don't show up in tests.
5. **Pre-deploy hooks aren't on all plans.** Migrations end up in `buildCommand`, so a failed migration breaks the build instead of failing safely after release. A foot-gun for a solo developer who hasn't internalized the build-vs-release distinction.
6. **USD-only billing.** EU operator pays FX volatility and handles VAT manually.

### Pre-Mortem — How This Could Fail

It's November 2026. Walkie has 200 owners and 50 walkers — modest traffic, but Solid Queue's in-process worker keeps thrashing the Basic-256MB Postgres connection pool every time multiple Owners create requests simultaneously. Sporadic `PG::ConnectionBad` 500s appear in production that never showed up in tests. You upgrade Postgres to Basic-1GB ($20) which solves the connection issue — but now you're at $27/mo and the dashboard shows persistent CPU saturation on Starter. You upgrade web to Standard ($25). The bill is $52/mo without warning, and the "$14/mo MVP" framing is gone. You consider migrating to Fly, but you wrote everything against Render's `render.yaml`, ditched the Kamal config months ago, and your migration scripts assume Render's pre-deploy semantics. Six months in, leaving costs a weekend you don't have and staying costs more than you budgeted. The cheapest viable choice quietly became one of the more expensive ones, one upgrade at a time.

### Unknown Unknowns

- **Render's "official Rails 8 guide" predates the Solid stack.** Edge cases (Solid Queue + connection pool, Solid Cable + WebSocket buffering through Render's proxy) are not pre-validated on the platform.
- **PG 17 availability on Basic tier is unverified.** The tech-stack pins PG 17; Render's Basic-256MB Postgres may still default to 16. Check the version selector before provisioning — adjust the tech-stack contract if PG 17 isn't available on the cheap tiers.
- **Disks block zero-downtime deploys.** Mounting a Render disk (tempting for Active Storage in dev) silently disables seamless production deploys. Not documented prominently.
- **Free Postgres expires in 30 days** (changed from 90 in May 2024). Any "quick test" PG vanishes in a month with a 14-day grace window — no automatic upgrade path.
- **Docs-MCP variant is experimental.** The main Render MCP server is GA, but the docs-MCP variant warns it "may be discontinued at any time". Build automation against the stable CLI surface, not against MCP mutation tools whose status hasn't stabilized.

## Operational Story

- **Preview deploys**: PR previews are a paid-plan feature (Pro tier). On Starter, branch builds don't get previews — you push to a `staging` Render service manually. Owner: solo developer; no team gating needed.
- **Secrets**: Stored as Render Environment Variables (encrypted at rest), set via dashboard or `render services update --env-var KEY=value`. `RAILS_MASTER_KEY` and `DATABASE_URL` are the load-bearing ones; `DATABASE_URL` is auto-populated when you link the Postgres add-on. GitHub Actions secrets are only needed if CI deploys via `render-cli` rather than git-push.
- **Rollback**: No first-class CLI command. Use `render deploys create --commit <sha>` against an earlier known-good commit, or click "Rollback to this deploy" in the dashboard. Time-to-revert: ~3–5 min on Starter (build + release). Migrations don't auto-revert — if a release ran a destructive migration, restore Postgres from the latest daily backup (Basic tier includes 7 daily snapshots).
- **Approval**: Auto-deploy on `git push` to `main` is the default. Toggle to **manual approval per deploy** in the service settings — recommended for production to enforce a human gate between agent-generated commits and live traffic. Destructive operations (delete service, drop database, rotate `RAILS_MASTER_KEY`) are dashboard-only and intentionally not exposed via the MCP server's mutation tools.
- **Logs**: `render logs --tail` streams live runtime logs; `render logs --tail --type=build` for build output; or via the MCP server's read-only log tools. Dashboard log retention: 7 days on Starter. Pipe to a longer-retention sink (Logtail, Better Stack) when you outgrow it.

## Getting Started

The project's `Dockerfile` (generated by the Rails 8 bootstrapper) is the entry point — **use the Dockerfile path, not Render's native Ruby buildpack**, because the native-runtime guide explicitly recommends `--skip-solid` and drops Thruster, neither of which fits Walkie's tech-stack contract.

1. **Install Render CLI**: `brew install render` (macOS) or download from [render.com/docs/cli](https://render.com/docs/cli). Verify: `render --version` (expect ≥ 2.18).
2. **Sign in and link the workspace**: `render login` (opens browser), then `render workspace set <workspace-name>`.
3. **Provision Postgres in Frankfurt**: From the dashboard, create a Basic-1GB Postgres in `frankfurt`. Note `DATABASE_URL` — Render will auto-link it to the web service when you create that next.
4. **Provision the web service** from this repo (the existing `Dockerfile` at repo root will be detected):
   - Service type: Web Service
   - Region: Frankfurt
   - Plan: Starter ($7/mo)
   - Branch: `main`
   - Auto-deploy: **off** at first (toggle on after the first successful deploy)
   - Health check path: `/up` (Rails 8 default)
   - Required env vars: `RAILS_MASTER_KEY` (from `config/master.key`), `WEB_CONCURRENCY=2`, `DATABASE_URL` (auto-linked from the Postgres add-on above)
5. **First deploy**: `render deploys create --service <service-id> --commit <sha> --confirm`. Watch logs with `render logs --tail`.
6. **Verify**: hit the service URL, confirm a `/up` 200 response. Run a smoke test through the walk-request flow once models exist.
7. **Wire the MCP server** (optional, for agent operability): `claude mcp add Render <render-mcp-config>` — see [render.com/docs/mcp-server](https://render.com/docs/mcp-server). API-key auth; never commit the key.

When ready to commit to auto-deploy on push: re-enable the Auto-Deploy toggle. Keep an explicit Plan-Mode review (host-level Plan Mode, not a skill) before the first push that goes through automated deploy.

## Out of Scope

This research did **not** evaluate:
- Docker image configuration or `Dockerfile` content (the Rails 8 bootstrapper's Dockerfile is taken as given).
- CI/CD pipeline setup (GitHub Actions config is a separate concern handled by the host's Plan Mode deploy step).
- Production-scale architecture: multi-region failover, HA, DR, SLA commitments.
- Long-term graduation plan from MVP-tier to production-tier infrastructure (revisit when traffic justifies it).
- Alternative deployment paths that keep Rails 8's default **Kamal** tool (would require a managed VPS like Hetzner + Kamal — a different platform category not in the candidate pool, and a deliberate skip given the user's preference for managed infrastructure).
